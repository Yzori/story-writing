### Applying an asset (or 'Add frames') to a panel with empty layout slots appends past the slot count — frame is invisible in the editor but renders in the reader
**Area:** webtoon-editor · **Location:** `src/components/editor/WebtoonEditor.tsx:1559`

handleApplyAssetToPanel does `frames = [...parseFrames(panel), {id, imageData}].slice(0, 6)` and keeps the existing layout whenever it is not 'single'. Storyboard panels — the default created by the left rail's '+ Panel' button and the 'Storyboard from script' flow — have layout 'top-pair-bottom' with 3 EMPTY frames stored in JSON. parseFrames returns those 3 empty frames, so the asset is appended as frame index 3 of a 3-slot layout. The editor canvas renders via ensureFramesForLayout (line 308), which truncates the array to the layout's slot count, so the just-applied asset is invisible: the user clicks an asset in the tray, sees a saving spinner, the PATCH succeeds, and nothing appears. Meanwhile the public reader does NOT truncate — it filters out empty frames (WebtoonReader.tsx:243) and renders the hidden 4th frame, so editor and published output diverge. handleAddFrames (line 1655) has the identical bug for the panel-toolbar 'Add frames' button. Additionally, when a panel already has 6 frames, `.slice(0, 6)` silently drops the newly added frame yet still PATCHes and reports success.

**Suggested fix:** Fill the first empty slot instead of appending (find index of first frame with imageData === ''), and only append when all slots are full (then grow the layout via getDefaultLayout). Surface an error when the 6-frame cap drops the new frame.

### Enter on an empty stanza line leaves phantom empty stanzas in the document (content corruption that persists to saved HTML)
**Area:** poetry-screenplay · **Location:** `src/components/editor/PoetryEditor.tsx:97`

The Stanza Enter handler's first branch (stanza with a single empty line, lines 90-111) does `tr.delete(pos, pos + currentLine.nodeSize)` to remove the empty line, then inserts a new empty stanza after. But the stanza schema is `content: "poetryLine+"`, so ProseMirror's replace-step fitter refills the stanza with a fresh empty poetryLine instead of emptying it — the delete is a no-op. I verified this empirically against the installed prosemirror packages: starting from doc(stanza(poetryLine)) the handler produces doc(stanza(poetryLine), stanza(poetryLine)). Every press of Enter on an empty stanza therefore spawns one more empty stanza; repeated presses accumulate `<div class="stanza"><div class="poetry-line"></div></div>` blocks that are serialized by onUpdate, saved to the chapter, and render as large blank gaps (2.5rem stanza margin + 1.85em line min-height) in both the editor and PoetryReader. The same defect fires in the 'middle' branch (lines 137-165) when the empty line is at index 0 of a multi-line stanza: `tr.delete(linePos, stanzaEnd - 1)` deletes everything in the stanza, the fitter refills it with an empty line, and the result is doc(stanza(emptyLine), stanza(restOfLines)) — a phantom empty stanza left above the split (also verified empirically). Concrete repro: press Enter at the start of a line to create an empty line above it, arrow up to that empty line, press Enter — an empty stanza is left behind; or just press Enter repeatedly in a fresh poem to stack empty stanzas.

**Suggested fix:** When the deletion would empty the stanza, delete the whole stanza node instead of just the line (e.g. `tr.delete($from.before(stanzaDepth), $from.after(stanzaDepth))` for the single-line case), or compute lineIndex===0 as its own branch that converts the existing stanza boundary rather than delete+insert.

### setContent in content-sync effect emits update (Tiptap v3 default) — opening a chapter triggers a phantom edit and autosave
**Area:** prose-illustrated · **Location:** `src/components/editor/ProseEditor.tsx:210`

ProseEditor.tsx:210 and IllustratedEditor.tsx:393 call editor.commands.setContent(newContent) with no options. In Tiptap v3 (project uses @tiptap/react ^3.20.1) setContent's emitUpdate defaults to TRUE (confirmed in @tiptap/core d.ts: '@default true'), unlike v2 where it was false. The sync effect compares editor.getHTML() against the content prop and calls setContent on mismatch. The stored DB content is server-sanitized and ALWAYS differs from Tiptap's normalized output for common documents: sanitizeHtml strips contenteditable="false" from scene-break divs (not in ALLOWED_ATTR), and comment spans lose data-thread-id and get unwrapped. So on every mount of a chapter containing a scene break or comment, setContent fires, emits onUpdate, and handleUpdateContent (write page line 1143) runs queueSave + scheduleSave — the chapter is PATCHed and its version bumped without the user typing a single character. Consequences: two collaborators merely OPENING the same chapter both auto-save it and one receives a false 409 'modified by another user' conflict; version history fills with no-op bumps; and because setContent also resets the selection, any keystroke landing in the commit-to-passive-effect window is clobbered with a caret jump.

**Suggested fix:** Call editor.commands.setContent(newContent || "", { emitUpdate: false }) in both editors (also fixes PoetryEditor/ScreenplayEditor if they share the pattern), and ideally only run the sync when the chapter identity changes rather than on every content echo.

### Server-authoritative roll trusts unvalidated, player-editable character stats — modifier is unclamped and untyped
**Area:** dice-rolls · **Location:** `src/app/api/stories/[storyId]/campaign/sessions/[sessionId]/turns/route.ts:486`

The whole point of the server-side roll resolution (comment at lines 468-472: 'the only way to prevent a player from forging a favorable tier or dodging a fatal failure') is defeated because the modifier input — the character's stats JSON — is fully player-controlled and never validated. `updatePlayerCharacterSchema` (src/lib/validations.ts:341) accepts `stats` as any string up to 10000 chars, and `parseStats` (src/types/campaign.ts:181) does `if (raw.approaches) return raw as CharacterStats;` with no shape, type, or range check. The legitimate creation UI (src/app/campaign/[storyId]/page.tsx:776-782) only ever produces approach values in {-1, 0, +2}, but a player can PATCH their own character with `{"approaches":{"Bold":99,"Keen":99,"Subtle":99},"aspect":"x"}` (character owner is allowed to edit stats — only `status` is GM-gated) and from then on every roll computes total = 2d6 + 99 >= 10, i.e. guaranteed 'success' tier, including on fatal-stakes rolls — exactly the forged-tier / dodged-fatal-failure outcome the server rolling was built to prevent. Additionally, non-numeric values corrupt data: with `{"approaches":{"Bold":"2"}}`, `approachMod` is the string "2", `modifier = "2" + 0` → "20", `total = r1 + r2 + "20"` → string concatenation like "720"; the stored roll metadata then has a string `total`, which fails `rollMetadataSchema` (z.number) on read, so `parseRollMetadata` returns null and the client throws 'Server returned an incomplete roll' (play page line 478-480) even though the turn persisted.

**Suggested fix:** Validate stats on write (zod schema for `{approaches: {Bold/Keen/Subtle: z.number().int().min(-1).max(2)}, aspect: string}` in create/updatePlayerCharacterSchema), and defensively clamp in the roll path: `const approachMod = typeof approaches[matchedApproach] === 'number' ? Math.max(-1, Math.min(2, approaches[matchedApproach])) : 0`.

### Audience Spark is committed even when the Ink Drop transfer fails — spectator gets a free spark and can never retry
**Area:** gameplay-state · **Location:** `src/app/api/stories/[storyId]/campaign/sessions/[sessionId]/spectate/floor-round/sparks/route.ts:125`

**Suggested fix:** Inside the transaction, when transferDrops returns an error, throw (or call tx.rollback()) so the spark insert is rolled back, and translate the thrown error to the 400 response outside the transaction.

### Drag reorder fires one PUT per position crossing — concurrent PUTs can interleave server-side and a failed one reverts to a stale snapshot
**Area:** webtoon-editor · **Location:** `src/components/editor/WebtoonEditor.tsx:1859`

Reorder.Group's onReorder fires on EVERY position crossing during a drag, and handleReorder issues a PUT /panels/reorder immediately each time. Dragging a panel from the bottom of a 10-panel episode to the top fires ~9 PUTs in under a second. Three concrete failure modes: (1) the server applies each request's per-panel updates with Promise.all and no transaction (panels/reorder/route.ts:82-88), so two overlapping PUTs can interleave row updates, leaving the DB with a mixed order (duplicate sortOrders) that differs from what the client shows — the corruption surfaces on next load; (2) the write rate limit is 30 req/60s (src/server/rate-limit.ts:136), so a couple of long drags plus normal caption PATCHes trip 429, which takes the .catch() path; (3) the catch restores `previousPanels`, a snapshot captured when THAT request started — if a later reorder or caption edit happened while the failed request was in flight, the revert clobbers it, snapping the board back to a stale state mid-drag.

**Suggested fix:** Persist once on drag end (Reorder.Item onDragEnd / pointer-up) instead of per onReorder event; keep onReorder purely local. Wrap the server-side updates in a transaction, and on failure re-fetch instead of restoring a captured snapshot.

<details><summary>Verifier note</summary>

Verified all three mechanics in the code.
